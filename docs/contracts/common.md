# Common contract semantics

Version: 0.1.0 · Baseline: CTO001-r1 · Status: PROPOSED. Public API major: `/api/v1`. These are documentation schemas, not implemented handlers or generated code.

## Schema notation and scalars

`Name { field: Type }` defines a closed JSON object: all fields are required; undeclared fields are rejected on requests. `Type|null` permits null. `Type[]` is an array. Literal alternatives use `|`. Explicitly described response-only fields cannot be submitted. Empty string is not null. Types in [api-v1](api-v1.md) are normative shapes; semantic constraints below and in linked specifications apply too.

| Type | Constraint |
| --- | --- |
| ID | UUID string, generated by server for resources; UUID submitted for client_record_id/idempotency key must be random, not encode personal data |
| Instant | RFC3339 UTC with `Z`, millisecond precision; server normalizes supported input to this form; no ambiguous local datetime |
| Date | `YYYY-MM-DD`; calendar date in Africa/Lagos where cohort/date is specified |
| Version | Exact immutable version string; contract 0.1.0, method `browser-http-0.1`, receipt `receipt-0.1`, aggregation `aggregate-0.1`, notice `contribution-0.1` are distinct identifiers |
| Operator | `mtn` / `airtel` / `glo` / `t2mobile`; display names are catalog data |
| AreaID | Stable opaque catalog string, 1–64 ASCII letters/digits/hyphen/underscore; active curated Lagos LGA only. No assumed official numeric IDs, no coordinates |
| UInt | JSON integer 0..9,007,199,254,740,991; field-specific tighter limits override |
| PositiveMs | Finite JSON number >0, maximum 30,000 for measured active phases; milliseconds, at most 3 decimal places |
| Mbps | Finite nonnegative JSON number; decimal megabits/second, display rounded separately from stored derivation |
| Sha256 | Lowercase 64-hex digest; hashes of evidence remain private |
| Text | Unicode plain text; count limits in Unicode code points, normalize line endings to LF; reject NUL and unsafe control characters except LF/tab; escape at every output boundary |

Metric zero is permitted only when its method can actually produce a valid zero; `null` with a state expresses unavailable/failed/unsupported. Throughput with zero received bytes is never a valid completed throughput result. Unknown location is null; do not invent Lagos coordinates. Observation time is device/user supplied, server receipt time is separate. No IMEI/IMSI/phone/fingerprint fields.

## HTTP conventions

HTTPS only. JSON request bodies use application/json; evidence bytes use their allowlisted media type. Success JSON uses `Success<T> { data: T, meta: Meta }`; `Meta { contract_version: "0.1.0", request_id: ID }`. Non-JSON downloads and 204 responses have no wrapper. Private responses carry `Cache-Control: private, no-store`; tokens, narratives and bodies must be redacted from logs. Request body max 64 KiB except explicitly capped file/measurement transport; max export input 20 selected resources, max list page 50. Accept one opaque cursor, default limit 20; invalid/expired cursor = 400, never arbitrary SQL filters. Sort private lists by created_at then id, descending; cursor binds owner/resource/filter and is opaque, not authorization.

Auth is server-managed cookies. Mutations require validated same-origin Origin plus CSRF protection bound to session; first-party guest bootstrap uses an anonymous bootstrap CSRF cookie/token from GET /session. Missing Origin is rejected for browser mutations; alternate native clients need a later contract. `X-CSRF-Token` is never an owner identity. Correlation IDs may be logged; private IDs in URL paths must be redacted from external analytics.

## Errors

`Failure { error: Error, meta: Meta }`

`Error { code: ErrorCode, message: Text, fields: FieldError[], retryable: boolean, retry_after_seconds: UInt|null }`

`FieldError { path: Text, code: "required"|"invalid"|"unsupported"|"too_large" }`; path names only, never rejected values. Message is safe display text, not a raw DB/stack error.

| HTTP | ErrorCode | Meaning |
| --- | --- | --- |
| 400 | bad_request | Invalid JSON/query/cursor/unknown field |
| 401 | session_required / session_expired | No usable authenticated ownership session |
| 403 | request_forbidden | CSRF/origin or prohibited operation; no resource existence information |
| 404 | not_found | Missing OR inaccessible owned resource; same shape/timing class |
| 409 | idempotency_conflict / operation_in_progress / version_conflict / receipt_consumed / record_retired / state_conflict | Conflicting payload, concurrent operation, stale revision, replay or lifecycle conflict; receipt errors only after ownership check |
| 410 | session_window_expired | Owned measurement transport capability expired; not generic private-resource enumeration |
| 413 | payload_too_large | Hard request/file limit exceeded |
| 415 | unsupported_media_type | Body/file format not allowed |
| 422 | validation_failed / unsupported_method / invalid_receipt | Semantic validation or invalid same-owner receipt; no hidden row details |
| 429 | rate_limited | Retry-After header matches retry_after_seconds; carrier NAT controls may use more than IP |
| 503 | temporarily_unavailable / capability_disabled | Service/phase not released or endpoint unhealthy; never fake successful persistence |

On 429 and retryable 503 set a bounded retry delay; otherwise retry_after_seconds is null. A retry never implicitly reruns a metered test or resubmits a complaint. Fetching hidden private IDs returns 404 after authentication, not revealing owner or deletion reasons.

Stateless POST /exports does not require an idempotency key: repeating it generates a new authorized snapshot and generation timestamp without persisting a dossier. It never uses a saved response body from the idempotency ledger. Session logout and measurement cancellation are idempotent state transitions and do not need stored sensitive response bodies.

## Idempotency and concurrency

All POSTs and PUTs that create/mutate domain state require `Idempotency-Key: ID`; guest bootstrap has the special binding described in auth-sessions.md. Key scope = verified owner + HTTP method + canonical route (including resource ID). Store validated normalized request digest and result reference atomically with mutation for 24 hours. Same key/same request returns the same status/resource while still authorized, with `Idempotency-Replayed: true`; different request = 409. A concurrent unfinished request returns 409 operation_in_progress with retry delay. Failures before mutation do not consume a key. Request digests must not be retained beyond the documented window.

Create incident/measurement also has owner-scoped `client_record_id` with durable uniqueness through its retention/replay-fence horizon; same ID plus different normalized content = 409, never update. This makes delayed offline retries safe beyond 24-hour key storage. On deletion keep only a minimal owner-bound keyed digest replay fence until the remaining maximum offline window (30 days), no narrative/metrics; reject resurrection with 409 record_retired. An explicit new record requires a new client_record_id. Clients abandon unsynced requests after 30 days and obtain a deliberate new save decision; server rejects creates whose declared client_created_at is older than 30 days or >5 minutes in the future. Client timestamps are not a security identity, so malicious new IDs remain subject to quotas.

PUT on an editable incident/consent requires numeric `expected_revision`; optimistic mismatch = 409 version_conflict. For consent withdrawal, conflict does not authorize leaving the UI “withdrawn”: refresh and retry the user's withdrawal intent until acknowledged, show pending meanwhile. Replaying a successful mutation must recheck current authorization and existence; do not return cached deleted data or reusable download credentials. DELETE is inherently idempotent: own live record/all-data returns 202 cleanup state; same existing owner-bound cleanup reference returns its state; other/missing resource = 404. Revoked account sessions cannot replay actions after all-data deletion.

## Compatibility

Before acceptance these contracts may change only via coordinated revision and review. After release, additive optional response fields can be minor changes; clients ignore unknown response fields but must not interpret unknown enum values as trusted/eligible. Required input fields, enum meanings, metric semantics, authorization changes and removals need a major API change or explicit migration plan. New method/receipt/notice/aggregation versions never silently reinterpret old records. Security denial fixes still require review/evidence and communication; they are not license for unilateral interface changes. Known unsupported method = 422; old supported read records retain their original labels.
