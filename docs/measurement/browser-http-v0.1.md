# Browser HTTP method — browser-http-0.1

Specification version: 0.1.0 · Baseline: CTO001-r1 · Status: **PROPOSED CALIBRATION METHOD, NOT VALIDATED FOR PUBLICATION**. Owner: Codex (server/method), Antigravity (browser implementation after review). A method version freezes calculation, phase plan, endpoint semantics and qualification, independently of API/UI versions.

## Purpose and limitations

Measure application-observed HTTP latency and bounded transfer throughput to one controlled endpoint. It does not measure ICMP ping, radio signal strength, total carrier-billed usage, tower performance, a general outage, or operator fault. Operator/LGA/mobile confirmation/VPN disclosure are user-reported. Browser timing/bytes are client observations that a malicious client can invent even with a real endpoint receipt.

No real metered tests are authorized by this document. F04 requires budget, target, supported browser matrix, endpoint region and pilot plan. No automatic background/repeat tests. User sees payload limit, likely duration, cancellation, operator/LGA choice, mobile confirmation and billing-overhead limitation before each session. Guest/session creation is disclosed; saving and contribution are separate actions. Manual LGA optional for private tests, mandatory for candidate public aggregation.

## Proposed fixed phase plan

| Order | Phase | Application payload | Deadline/measurement |
| --- | --- | --- | --- |
| 1 | Five sequential latency requests | Empty request and response bodies | Each at most 2,000 ms; first cold request recorded privately, remaining four warmed samples |
| 2 | One download | 12,582,912 bytes (12 MiB) incompressible fixed length | At most 15,000 ms and remaining session time |
| 3 | Optional upload | 4,194,304 bytes (4 MiB) non-sensitive generated bytes | At most 10,000 ms and remaining session time; server counts/discards |

Hard total active-session deadline is 30,000 ms from first server-accepted phase; per-phase deadlines cannot extend it. Max concurrent transfer/request =1. No retries or warm-up data transfers in this version. The latency cold sample is the only connection warm-up; it is not included in displayed warmed latency. Maximum transfer payload =16,777,216 bytes (16 MiB); without upload =12 MiB. HTTP headers, TLS/IP overhead and control/receipt requests are outside this payload budget, so carrier usage can be higher. Do not market it as a strict billed-data cap. Bound control responses separately to 16 KiB each, receipt polling at most once per second and 10 attempts; no unlimited payload by error handling.

A session must start within 60 seconds of issuance. Expiry, quotas, per-slot once-only semantics and concurrency are server-enforced; the browser separately aborts locally. Phase slot tokens authorize only one fixed-size phase on this endpoint; they confer no incident/history access. On failure/cancellation, no automatic new session. Retrying requires a new explicit metered-test confirmation.

## Transport

Under the controlled endpoint, proposed paths are `/measure/v1/sessions/{session_id}/slots/{slot_id}`: POST for latency (204 empty), GET for download (200 bytes), PUT for upload (200 small JSON acknowledgement). POST `/measure/v1/sessions/{session_id}/cancel` aborts remaining slots and returns 204. Slot requests use Authorization Bearer one_use_token (not the Supabase token); cancellation uses the active same-origin owner session and CSRF. No tokens in URLs. Cross-origin deployment requires a separately reviewed CORS/cookie/cancel adapter; do not silently loosen origin policy.

Download returns exact declared length with compression disabled and no CDN/browser/service-worker cache. Count stream bytes read, not Content-Length alone. Control request redirects are rejected; no redirects to arbitrary third-party hosts. Endpoint cannot fetch a supplied URL, vary size from query params, reflect user bodies, or retain upload contents. Record actual bytes the application endpoint wrote/received plus its monotonic durations, not inferred socket/radio delivery. Buffering at a reverse proxy must be detected during calibration; server timings do not bypass it by assertion.

Browser uses performance.now or equivalent monotonic time; do not subtract wall clocks for elapsed time. Store wall start/end separately as user-device observations. Request timeouts or cancellation yield failed/cancelled phases, not zeros. Visibility loss or disclosed connection change flags the whole candidate record as interrupted. Unsupported upload is explicitly not attempted; it must not fabricate zero performance.

## Calculations and result state

Latency duration = immediately before fetch initiation to completion of response body consumption for each slot. Completed warm samples must be four finite positive durations; median of those four is displayed (middle two average). The first/cold duration stays in private raw observations. If fewer than four warm samples complete, latency value=null and state=failed/cancelled as applicable; partial timings can be shown privately with limitations but are not a completed metric.

Download duration = fetch initiation to last body byte read, including response startup. Throughput = actual body bytes *8 /(duration_ms/1000)/1,000,000. A completed download requires all 12 MiB read and a server-completed matching slot. For a client_only record, the client can report completion but the result is explicitly uncorroborated; do not assert server completion. Less than 1,000 ms is a resolution/saturation concern in this small test and disqualifies public download, even if numerically calculable. Results at/over the deadline or with partial bytes have no successful throughput. This is bounded-test experience, not proof of saturated line capacity.

Upload application-observed duration = before PUT initiation until the acknowledgement body arrives; acknowledgement is generated only after server consumes exactly 4 MiB. Browser metric is accepted bytes divided by this roundtrip-inclusive duration, never time-to-queue-body. Server additionally measures time from first to last body chunk received; this is a distinct endpoint observation and must not be substituted for browser upload rate. Full buffering can make server receive duration meaningless for the mobile path. All upload results are private in this method version; publication requires a later validated method/decision.

Every Metric has unit ms for latency or Mbps for transfers. value is null unless that metric completed under its defined semantics. Server recomputes values from browser samples and trusted accepted-upload byte count where a receipt exists; recomputing cannot establish that browser timing is honest. Do not silently clamp impossible numbers into valid ones.

Overall state: completed when latency/download and any requested upload completed; partial when at least one metric completed and another requested metric did not; cancelled when none completed and user cancellation ended the test; failed otherwise. not_run/unsupported optional upload does not make an otherwise complete latency/download test partial. A partial upload may leave completed download/latency independently eligible if their phases and the overall visibility/endpoint checks passed. Public qualification is per metric, not a single success badge.

## Qualification inputs

Use server session start for cohort time; browser clock mismatch >5 minutes sets client_clock_skew and excludes candidate publication until method review, but private evidence preserves both times. Exact bounds on bytes, phase counts, positive durations and supported endpoint/method are structural validation. Completed-metric agreement with receipt, mobile confirmation, area, VPN=no, no visibility/connection interruption and no endpoint incident are qualification checks. VPN=no remains a user assertion, not a detection result. Suspicious timing cannot be “verified” solely by passing a range check.

No upper Mbps gate is invented without pilot data beyond the minimum-duration rule; real network extremes must not be silently discarded. Endpoint health is a server signal; unknown health disqualifies public use. The client never controls moderation or public eligibility. See [receipt specification](receipt-v0.1.md) and [aggregation contract](../contracts/aggregation.md).

## Calibration and change gate

Later authorized pilot must compare this bounded method with a trusted reference under controlled conditions, disclose endpoint geography and peering, include supported Android browsers and iOS/Safari, all four target operators where accessible, cold/warm paths, low throughput, tab suspension, endpoint overload, compression/cache faults and upload buffering. Record bias/range/variance, byte consumption and cancellation overshoot. Test localhost emulation is insufficient for public credibility.

Unresolved parameters are founder-budget and CTO-calibration decisions, not latent implementation freedom. Any change to payload sizes, connection count, timing boundaries, warm-up, minimum duration, endpoint transfer semantics or aggregation eligibility creates a new method revision and separate comparable series. No native Android measurements are compatible by default. Acceptance examples: 12,582,912 bytes over 2,000 ms yields 50.331648 Mbps; zero duration rejected; same bytes over 500 ms can be private but has duration_too_short; server sent12 MiB/client read6 MiB cannot be a completed matched download.
